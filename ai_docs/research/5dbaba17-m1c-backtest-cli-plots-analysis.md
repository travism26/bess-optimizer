## Executive Summary

M1c is the integration task that closes M1: three stub functions
(`run_backtest`, `plot_dispatch_detail`, `plot_cumulative_revenue`), two stub
CLI commands (`bess backtest`, `bess plot`), one all-TODO test file, and the
README results section. Both upstream layers are merged and working, so nothing
existing needs refactoring; every touched symbol currently raises
`NotImplementedError` or is a comment.

I ran the real LP over the committed HB_NORTH July 2023 fixture to pre-validate
the acceptance corridor: status optimal, total revenue **$970,937.15**,
**6,635.40 MWh** discharged, **33.18** equivalent full cycles (AC-2 corridor is
5 to 60, comfortably inside), $146.33 per MWh discharged, $114,320 per MW-year
annualized from 744 hours, `simultaneous_hours == 0`, solve time ~0.008 s. Two
consecutive solves are bit-identical, so AC-4 determinism is achievable.

Two findings will cost the build phase real time. First, **AC-3 and AC-4
contradict each other**: AC-3 requires `solve_time_seconds` in the metrics JSON
and AC-4 requires two consecutive runs to be byte-identical, which a wall-clock
measurement never is. Second, **`bess backtest` must not be allowed to fetch**:
the default `config.toml` window (2023-2024, three hubs) has no cache on disk,
so a naive call to `fetch_da_prices` would hit the network, which the conftest
guard turns into a hard test failure and CI cannot do at all.

## Impact Analysis

### Scope of Change

Medium and almost entirely additive: roughly 250 to 350 lines of implementation
across three modules plus 250 to 350 lines of tests, no refactoring of merged
code. The riskiest parts are not algorithmic; they are the JSON contract
(determinism), the CLI's offline guarantee, and the README numbers.

### Risks and Considerations

**1. AC-3 versus AC-4 is a genuine spec contradiction (highest priority
decision).** AC-3 requires the metrics JSON to contain every metric "in
criterion-2 scope above", which includes "solve wall time"; master AC-7 also
requires the actual time to be recorded there. AC-4 requires two consecutive
runs to produce byte-identical JSON after key sorting. A wall-clock measurement
is never byte-identical across runs. Everything else is deterministic: I ran the
LP twice on the fixture and the charge, discharge, and SoC arrays plus the
objective compared exactly equal. Recommended resolution: keep
`solve_time_seconds` in the JSON as required, and have the determinism test
compare the two payloads with that one key removed, with a comment in the test
naming the AC-3/AC-4 tension. Alternatives considered and rejected: dropping the
field (breaks AC-3 and master AC-7); rounding to whole seconds (still flaky
across machines and near boundaries).

**2. `bess backtest` must never fetch.** The default config's window and hubs
are not cached, so calling `fetch_da_prices` from the backtest command would
fall through to gridstatus. That would fail the conftest guard in tests, fail
outright in CI, and violate the module docstring in `cli.py` ("backtest and plot
run entirely from the parquet cache"). Recommended: check
`_cache_path(...).exists()` (or a new public `load_cached_prices` helper in
`data/prices.py`) and raise a clear "no cached prices for X, run `bess fetch`
first" error. Verified working: copying the fixture to
`<cache_dir>/HB_NORTH_2023-07-01_2023-07-31.parquet` makes `fetch_da_prices`
serve a 744-row frame entirely from cache with the network guard armed.

**3. Daily-revenue day boundary changes the row count (gotcha 2).** On the
fixture, grouping `interval_start_utc` by **Central** local date gives exactly
31 days (2023-07-01 through 2023-07-31, summing to the full $970,937.15);
grouping by **UTC** date gives 32 days, with a 19-hour first day and a 5-hour
last day. ERCOT's market day is Central and the fixture window was sliced on
Central days in `_canonicalize`, so Central is the coherent choice. The spec
allows either, but demands the docstring say which. To respect the CLAUDE.md
rule that timezone knowledge lives in `data/prices.py`, source the zone from
there (promote the existing `_CENTRAL_TZ` to a public `MARKET_TZ`) rather than
hardcoding a second copy of the string in the runner.

**4. Annualization (gotcha 1).** `revenue_per_mw_year = total_revenue /
power_mw * (HOURS_PER_YEAR / window_hours)` where `window_hours = len(prices) *
dt_hours` (744 for the fixture), and `HOURS_PER_YEAR = 8760.0` as a named
constant. The spec's "not hardcoded to 8760" means the *window* must not be
assumed to be a year; the 8760 hours-per-year scaling constant itself is
correct. Do not derive window hours from a calendar-day count: DST days have 23
or 25 hours. Deriving from the row count (or equivalently
`interval_end_utc.iloc[-1] - interval_start_utc.iloc[0]`) is DST-safe because
everything is already UTC. Expected value on the fixture: **$114,320.02 per
MW-year**.

**5. Division by zero with a stub optimizer (AC-5).** `revenue_per_mwh_discharged`
and `equivalent_full_cycles` divide by discharged MWh and `energy_mwh`. A stub
optimizer that returns all-zero arrays (the obvious way to write the AC-5 test)
makes the first one `0/0`. Guard explicitly and return `0.0` when nothing was
discharged, rather than emitting `NaN` or `Infinity` into JSON (`json.dumps`
writes bare `NaN`/`Infinity`, which is not valid JSON for strict parsers).

**6. Proving the injected optimizer is actually used (AC-5).** Because
`optimizer=optimize_dispatch` is bound as a default argument at definition time,
`monkeypatch.setattr("bess.backtest.runner.optimize_dispatch", ...)` will **not**
intercept anything, and patching `bess.optimizer.lp.optimize_dispatch` will not
either. To prove the real LP was not touched, monkeypatch `highspy.Highs` to
raise, or assert on a call counter inside the stub plus identity of the returned
arrays. The stub must return arrays of length T, or the revenue math breaks.

**7. Matplotlib backend.** The default backend here is `macosx`, which is a GUI
backend; `pyplot` on a headless CI runner or a non-main thread is a classic
source of flakes and leaked figures. Use the object-oriented API
(`from matplotlib.figure import Figure`, `fig.subplots()`, `fig.savefig(...)`)
and never import `pyplot`. Verified: this path renders without a display and
without `matplotlib.use("Agg")`. Sizes at `dpi=100` are comfortably over the
AC-6 10 KB floor: 54,493 bytes for a 7-day dispatch detail with a twin SoC axis,
28,849 bytes for a single-hub cumulative revenue line.

**8. The fixture cannot exercise every metric.** HB_NORTH July 2023 has no
negative prices (minimum $12.91) and yields `simultaneous_hours == 0`. That is
correct, not a bug, but it means the metrics JSON will show zero there and no
integration test can assert a nonzero value from the fixture. Simultaneity is
already covered by the M1b unit test; do not contrive a fixture change for it.

**9. The `bess plot` input contract.** `BacktestResult` carries `daily_revenue`
(enough for the cumulative plot) but not the dispatch arrays (needed for the
7-day detail). Options: have `bess backtest` persist a per-location dispatch
frame that `plot` reads, or have `plot` re-run the solve. Persisting is
preferable, it matches the spec wording ("renders both PNGs from a
metrics/dispatch output"), and a parquet dispatch file is auto-ignored by the
existing `*.parquet` rule. Note master AC-8 requires `bess backtest` **itself**
to produce both PNGs, so `backtest` calls the plot functions too and `plot`
is the standalone re-render path.

**10. README numbers: master DoD versus M1c AC-8.** The master DoD asks for
"revenue per MW-year by hub by year" (three hubs, two years) and the current
README placeholder table is shaped that way. That data does not exist offline;
only the one fixture month is committed. M1c AC-8 is the more specific and
achievable requirement: "a small table (revenue, revenue per MW-year, cycles for
the fixture month) and both plots embedded". Recommendation: replace the
placeholder with the fixture-month table, and add one sentence saying the full
2023-2024 three-hub table requires `bess fetch` (network) and is not reproducible
from the repo alone. Flag the deviation from the master DoD wording in the PR
rather than silently narrowing it.

**11. README images must be tracked files.** Embedding plots means committing
two PNGs (roughly 30 to 55 KB each, in line with the already-tracked ~21 KB
fixture). Put them under a tracked path such as `docs/img/`, keep the CLI's
default output directory separate, and add that output directory to
`.gitignore`.

**12. JSON serialization details.** numpy scalars are not JSON-serializable;
cast with `float()`/`int()`. Serialize `daily_revenue` as an object keyed by ISO
date strings. Use `json.dumps(..., indent=2, sort_keys=True)` plus a trailing
newline so AC-4's "byte-identical after key sorting" is literal rather than
requiring a custom comparator. `allow_nan=False` is a cheap way to make risk 5
fail loudly instead of writing invalid JSON.

**13. `dt_hours` derivation.** Compute from the data rather than assuming 1.0:
take the unique diffs of `interval_start_utc` and require exactly one value
(verified: the fixture has exactly one, `01:00:00`), falling back to
`interval_end_utc - interval_start_utc` for a single-row frame. Being in UTC is
what makes this DST-safe. Raise on non-uniform spacing rather than silently
averaging.

**14. Test assertions and LP degeneracy.** Per the prior memory lesson, assert
metric-level and aggregate quantities (total revenue, cycles, SoC bounds,
dynamics residual, revenue identity) and never a specific per-interval schedule.
The AC-2 corridor is deliberately wide for the same reason.

**15. Housekeeping.** `.ports.env` is already modified in this worktree (`git
diff --stat` shows 3 insertions, 3 deletions). This has been flagged in both
prior reviews and never fixed. Restore or untrack it before finalizing. Also
delete the four scaffold TODO comments in `tests/test_backtest_integration.py`
as their criteria land (M1a review issue #3), keep to ruff's 100-column limit
and rule set `E, W, F, I, B, UP, SIM, RUF`, and use no em-dashes.

**16. mypy.** I probed a representative slice (pandas `groupby` on a
tz-converted date index, `Series.items()` JSON round-trip, matplotlib `Figure`
plus `savefig`) under the project's exact flags (`disallow_untyped_defs`,
`warn_return_any`, `strict_equality`, with `pandas-stubs` installed) and it
passed clean. matplotlib 3.11.1 ships `py.typed`, so no new override in
`pyproject.toml` is needed. Expect the usual friction only where numpy scalars
meet the frozen `float` fields; explicit `float(...)` casts settle it, exactly as
`lp.py` already does.

### Existing Patterns to Follow

- Module docstring states purpose and cites the spec section it implements
  (`data/prices.py` is the model).
- `from __future__ import annotations` at the top of every module and test file.
- Module-level `logger = logging.getLogger(__name__)`, no `basicConfig`.
- Private helpers prefixed with `_`, imported by name in tests where useful
  (`_canonicalize`, `_validate`, `_cache_path`).
- Test docstrings name the acceptance criterion they cover ("AC-4: ...").
- Every test function annotated `-> None`; mypy checks `tests/` too.
- Failures raise `ValueError` (data problems) or `RuntimeError` (solver
  problems) with a message naming the offending values.
- CLI options use the `Annotated[...]` + `typer.Option` style and a
  config-then-flag precedence, with non-spec config keys commented as such.
- Constants for magic numbers at module scope with a comment citing the spec
  (`_SIMULTANEOUS_THRESHOLD_MW` is the precedent).

| Metric | Value |
| ------ | ----- |
| `solver_status` | `optimal` |
| `total_revenue_usd` | 970,937.15 |
| `total_discharged_mwh` | 6,635.40 |
| `equivalent_full_cycles` | 33.18 (AC-2 corridor: 5 to 60) |
| `revenue_per_mwh_discharged` | 146.33 |

### Implementation shape

1. **`run_backtest`.** Validate the frame is single-location and non-empty,
   derive `dt_hours`, pull `prices = df["price"].to_numpy(dtype=float)`, time the
   `optimizer(prices, dt_hours, battery)` call with `time.perf_counter()`, then
   compute metrics from the returned arrays (not from the solver objective, so
   any injected optimizer works), and log a WARNING if the recomputed revenue
   and `objective_value` disagree beyond 1e-4. Per-interval revenue is
   `prices * (discharge_mw - charge_mw) * dt_hours`, which is the array the daily
   series groups.
2. **Metric helpers.** Keep `_daily_revenue`, `_annualize`, and the safe-divide
   as small module-level functions so M2's rolling horizon can reuse them and so
   tests can hit them directly.
3. **Plots.** Object-oriented matplotlib only. Dispatch detail: two stacked
   panels sharing the x axis (price on top; charge as positive bars and
   discharge as negative bars below, with SoC on a twin axis), default window
   start = first day of the horizon, `window_days=7`, `dpi=100`, and
   `fig.savefig(output_path)` returning `output_path`. Cumulative revenue: one
   `cumsum()` line per hub with a legend, which degrades correctly to a single
   line when only HB_NORTH is present.
4. **CLI.** `backtest` writes, per location, `<location>_metrics.json` and a
   dispatch artifact, plus one combined comparison table across locations
   (markdown is the most useful form here since it drops straight into the
   README) and both PNGs; `plot` re-renders the PNGs from those artifacts. Add an
   `--output-dir` flag with a config-key fallback, mirroring how `cache_dir` was
   introduced, and comment that the key is outside the frozen config list.
5. **Failure modes.** Missing cache file, empty frame, multiple locations in one
   frame, and non-uniform interval spacing all raise with a message naming the
   location and the offending value.
